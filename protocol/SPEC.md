# yikz-clipboard wire protocol, version 1

Status: normative. This document and the files in `protocol/vectors/` are the single source of truth for the Go server, the Svelte web client, the Swift macOS client, the Kotlin Android client and the C# Windows client. Where prose and a vector disagree, the vector wins and the prose is a bug.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as in RFC 2119.

## 1. Conventions

- **JSON**: UTF-8, no BOM. Object field order is not significant. Receivers MUST ignore unknown fields. Senders MUST NOT send `null` for a field unless this document says the field is nullable.
- **Integers**: JSON numbers without fraction or exponent. All integer values (seq, sizes, byte counts) stay below 2^53 so JavaScript can represent them exactly.
- **Base64**: RFC 4648 standard alphabet (`+` and `/`) with `=` padding, no line breaks. Decoders MUST reject input that is not valid padded standard base64. Used for every sealed box inside JSON (`meta`, `payload`) and for the account `salt`.
- **Base64url**: RFC 4648 URL-safe alphabet without padding. Used only inside tokens.
- **Hex**: lowercase `0-9a-f`. Used for `content_hash`, `key_check`, `meta.sha256`.
- **Timestamps**: RFC 3339 in UTC with exactly three fractional digits and a `Z` suffix, for example `2026-09-21T10:00:01.250Z`. Servers MUST emit exactly this form. Clients MUST emit it too and MUST parse any valid RFC 3339 timestamp.
- **Sizes**: `KiB` = 1024, `MiB` = 1048576, `GiB` = 1073741824 bytes. The environment variables named `*_GB` are interpreted as GiB (for example `CC_STORAGE_MAX_GB=5` means 5368709120 bytes).
- **Strings in lengths**: "code points" means Unicode scalar values (not UTF-16 units, not grapheme clusters).
- **Transport**: HTTPS and WSS in production. The server listens on plain HTTP behind nginx. All paths below are relative to the server origin, for example `https://clip.yikz.dev`.

## 3. Identifiers

### 3.1 Item ids

Item ids are UUIDv7 (RFC 9562) generated by the **client** that creates the item, rendered as lowercase 8-4-4-4-12 hex with hyphens:

```
bytes 0..5   unix time in milliseconds, 48-bit big-endian
bytes 6..15  random bytes, then
             byte 6 = 0x70 | (byte 6 & 0x0f)   (version 7)
             byte 8 = 0x80 | (byte 8 & 0x3f)   (variant 10)
```

Valid ids match exactly `^[0-9a-f]{8}-[0-9a-f]{4}-7[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`. The server MUST reject any other form in a path or body with `400 invalid_id` (uppercase, braces, missing hyphens and other versions are all invalid). The random part MUST come from a CSPRNG. The timestamp in an id is informational only; ordering always uses `seq`.

### 3.2 Device ids and server id

Device ids are UUIDv7 generated by the **server** at first login of a device. `server_id` is a UUIDv7 generated once when the server first initializes its data directory and never changes afterwards. A different `server_id` means the server data was wiped (see 11.2).

### 3.3 seq

`seq` is a signed 64-bit integer assigned by the server when an item becomes committed. It starts at 1 and is strictly increasing across the whole account. It is never reused, even after the item is deleted. `current_seq` is the highest seq ever assigned (0 if none).

### 3.4 state_rev

`state_rev` is a server counter (int64, starts at 0) that increments by exactly 1 for every `clip_deleted` or `clip_pinned` event the server emits (one increment per event, regardless of how many ids it carries). Committing a new item does not change `state_rev`. It lets clients detect that they missed deletions or pin changes while offline.

## 4. Authentication and devices

### 4.1 Account

There is exactly one account. Its username and login password come from `CC_USERNAME` and `CC_PASSWORD`. At first run the server generates and persists:

- `salt`: 16 bytes from a CSPRNG (the account encryption salt).
- `server_id`: a UUIDv7.

Both never change afterwards. The server also stores an optional `key_check` (section 5.4), initially absent.

### 4.2 Device tokens

```
token      = "yc_" + base64url_nopad(32 random bytes)     (46 ASCII chars)
token_hash = lowercase hex SHA-256 of the token's ASCII bytes
```

Tokens match `^yc_[A-Za-z0-9_-]{43}$`. The server stores only `token_hash`, never the token. Tokens do not expire; they are valid until revoked. Each device has at most one valid token.

Clients send the token as `Authorization: Bearer <token>` on every authenticated HTTP request and on the WebSocket upgrade request. Because browsers cannot set headers on WebSocket upgrades, the server also accepts `?token=<token>` as a query parameter on every authenticated endpoint. Clients other than the web client MUST use the header. The web client MUST use the header for `fetch` and MAY use the query parameter only for `/ws`. The server MUST redact the query parameter in logs. If both are present the header wins.

Token storage: macOS Keychain, Windows Credential Locker (PasswordVault), Android EncryptedSharedPreferences or Keystore, web `localStorage`.

Any `401` from an endpoint other than `/api/login` means the token is missing, invalid or revoked. The client MUST stop the WebSocket, delete the token and ask the user to log in again.

### 4.3 POST /api/login

No authentication. Request:

```json
{
  "username": "thoriq",
  "password": "login-password-example",
  "device_name": "Thoriq MacBook Pro",
  "platform": "macos",
  "device_id": "01a05c04-97c0-7c1c-bdb7-1933ae6945c4"
}
```

| Field | Type | Rules |
|---|---|---|
| `username` | string | required |
| `password` | string | required, the login password (never the encryption password) |
| `device_name` | string | required, 1 to 64 code points after trimming leading and trailing whitespace, no control characters |
| `platform` | string | required, one of `macos`, `android`, `windows`, `web` |
| `device_id` | string | optional, the device id this client received earlier |

Behavior:

1. Validate the body (`400 invalid_request` on failure, including an unknown platform).
2. Rate limit: after 10 failed logins from the same client IP within 10 minutes, respond `429 rate_limited` with a `Retry-After` header (seconds) until the window frees. Honor `X-Forwarded-For` only from the configured reverse proxy.
3. Compare username and password in constant time. Mismatch gives `401 invalid_credentials`.
4. If `device_id` is present and names an existing device (revoked or not), reuse it: set its name and platform from the request, clear its revoked flag, invalidate its previous token (closing its WebSocket connections with close code 4001). Otherwise create a new device with a new server-generated id. An unknown `device_id` is not an error.
5. Issue a fresh token and emit `devices_changed` on the WebSocket.

Response `200`:

| Field | Type | Meaning |
|---|---|---|
| `device_id` | string | the device id to persist |
| `token` | string | the device token to persist in secure storage |
| `username` | string | account username |
| `salt` | string | base64 of the 16-byte account salt |
| `kdf` | object | `{"algorithm":"pbkdf2-sha256","iterations":600000,"key_length":32}` |
| `key_check` | string or null | stored key check (64 hex chars), `null` when not yet set |
| `server_id` | string | see 3.2 |
| `server_version` | string | server build version, informational |
| `protocol_version` | integer | `1` |

Clients MUST refuse to continue when `kdf.algorithm` is not `pbkdf2-sha256`, `kdf.key_length` is not 32, or `protocol_version` is not 1. See vectors `login_new_device`, `login_existing_device`, `login_invalid_credentials`, `login_invalid_platform`, `login_rate_limited`.

### 4.4 GET /api/me

Authenticated. Response `200` with `username`, `device` (a device object with `current: true`), `salt`, `kdf`, `key_check` (nullable), `server_id`, `server_version`, `protocol_version`, and `limits`:

```json
{
  "inline_max_bytes": 262144, "chunk_size_bytes": 4194304, "max_chunk_body_bytes": 4194332,
  "thumb_max_bytes": 65536, "meta_max_bytes": 65536, "max_json_body_bytes": 1048576,
  "max_files_per_item": 1000, "history_default_limit": 100, "history_max_limit": 500,
  "max_ws_client_frame_bytes": 65536, "max_ws_server_frame_bytes": 1048576,
  "max_connections_per_device": 8, "upload_ttl_seconds": 3600, "disk_low_max_upload_bytes": 1048576
}
```

Also used by the web client to tell a failed WebSocket upgrade caused by a bad token (`401`) from a network failure.

### 4.5 POST /api/logout

Authenticated, no body. Revokes the calling device exactly like `DELETE /api/devices/{own id}` and responds `204`. The client MUST delete its token and derived key and SHOULD clear its local history cache.

### 4.6 Key check endpoints

- `PUT /api/account/key-check` with `{"key_check": "<64 hex>"}`. If no key check is stored, store it and respond `204`. If the same value is stored, respond `204`. If a different value is stored, respond `409 key_check_exists`.
- `DELETE /api/account/key-check`. Allowed only when the account has no items at all (committed or pending): responds `204` and clears the stored value. Otherwise `409 items_exist`. This is the only way to change the encryption password: delete every item, reset the key check, then set a new one.

### 4.7 Devices

Device object (used by `/api/devices` and `/api/me`):

| Field | Type | Meaning |
|---|---|---|
| `id` | string | device id |
| `name` | string | device name |
| `platform` | string | `macos`, `android`, `windows`, `web` |
| `created_at` | timestamp | first login |
| `last_seen_at` | timestamp | last authenticated request or WebSocket activity (server MAY update at most once per minute) |
| `online` | bool | the device has at least one WebSocket connection that received `welcome` |
| `revoked` | bool | the device token was revoked |
| `current` | bool | this device is the caller |

Endpoints (all authenticated):

- `GET /api/devices` responds `200 {"devices": [...]}`, ordered by `created_at` ascending.
- `PATCH /api/devices/{id}` with `{"name": "..."}` (same rules as `device_name`) responds `200` with the updated device object. Unknown id gives `404 not_found`.
- `DELETE /api/devices/{id}` responds `204`. If the device is not revoked it becomes revoked: its token is invalidated and all its WebSocket connections are closed with code 4001. If it is already revoked, the device record is removed. Items created by a removed device keep their `device_id`. Unknown id gives `404 not_found`. A device may revoke itself.

Every create, rename, revoke or removal emits `devices_changed` on the WebSocket.

## 5. Cryptography

All content is end-to-end encrypted. The server never sees the encryption password, the key, or any plaintext besides the header fields listed in 6.1.

### 5.1 Key derivation

```
password_bytes = UTF-8( NFC( encryption_password ) )
K = PBKDF2-HMAC-SHA256(password_bytes, salt, iterations = 600000, dkLen = 32)
```

- The encryption password is separate from the login password and MUST never be sent to the server.
- The password MUST be normalized to Unicode NFC before encoding (vector `kdf.json` case `unicode_nfd_input`). No trimming.
- `salt` is the 16 decoded bytes of `salt` from login or `/api/me`.
- The derived `K` is stored in the device's secure storage. Clients derive it once, not on every launch.
- Platform APIs: CommonCrypto `CCKeyDerivationPBKDF` (macOS), `javax.crypto` `PBKDF2WithHmacSHA256` (Android; it takes a `char[]`, so it MAY be used only if it passes the `unicode_nfd_input` vector, otherwise compute PBKDF2 over the UTF-8 bytes directly), `Rfc2898DeriveBytes.Pbkdf2` with `HashAlgorithmName.SHA256` (.NET), WebCrypto `deriveBits` (web).

### 5.2 Subkeys

```
content_hash_key = HMAC-SHA256(K, UTF-8 "yikz-clipboard/v1/content-hash")
key_check        = hex( HMAC-SHA256(K, UTF-8 "yikz-clipboard/v1/key-check") )
```

### 5.3 content_hash

```
content_hash = hex( HMAC-SHA256(content_hash_key, content) )
```

`content` is the full plaintext content bytes of an item as defined in 6.3 (UTF-8 text, PNG bytes, or the YCF1 archive). The hash is keyed so the server can compare items for dedupe without being able to confirm guesses of the content. It is sent in the clear as an item header field. Separately, `meta.sha256` (inside encrypted meta) is the plain SHA-256 of the same content and is used to verify downloads.

### 5.4 Key check (wrong password detection)

`key_check` (5.2) is stored on the server. It reveals nothing useful about `K` but lets every client detect a wrong encryption password before it encrypts or decrypts anything:

1. After the user enters the encryption password, derive `K` and compute `key_check`.
2. If the server's `key_check` (from login or `/api/me`) is `null`, call `PUT /api/account/key-check`. On `204` accept `K`. On `409 key_check_exists` (another device set it first) re-fetch `/api/me` and compare.
3. If the server's value is present and equal, accept `K`. If it differs, the password is wrong: discard `K`, do not store it, and ask again.

The server rejects item creation, commit, and chunk and thumb uploads with `409 key_check_missing` while no key check is stored.

### 5.5 AEAD and sealed layout

Every encrypted object is an AES-256-GCM sealed box:

```
sealed = nonce (12 bytes) || ciphertext (same length as plaintext) || tag (16 bytes)
len(sealed) = len(plaintext) + 28
```

- The nonce MUST be 12 fresh bytes from a CSPRNG for every seal. Never reuse a nonce, including on retries of a new encryption (retrying an upload of the same sealed bytes is fine).
- The tag length is 128 bits.
- In JSON, a sealed box is base64 (section 1). In HTTP bodies (chunks, thumbnails) it is raw bytes.
- A sealed box shorter than 28 bytes is invalid. Any authentication failure MUST be treated as corrupt data: do not use partial output, do not write to the clipboard, and log it.

### 5.6 AAD

The additional authenticated data binds each sealed box to its item and role, so the server cannot swap, reorder, truncate or move sealed objects. AAD is the UTF-8 bytes of:

| Object | AAD |
|---|---|
| Meta | `yc1\|meta\|<item_id>` |
| Inline payload | `yc1\|payload\|<item_id>` |
| Thumbnail | `yc1\|thumb\|<item_id>` |
| Chunk | `yc1\|chunk\|<item_id>\|<index>\|<chunk_count>` |

(The backslashes above are Markdown escapes; the separator is a single `|`, byte 0x7C.) `<item_id>` is the lowercase id, `<index>` and `<chunk_count>` are base-10 integers without leading zeros or signs. Example: `yc1|chunk|01a0c36d-10e0-7a56-86e3-483e2f79d9c5|2|3`.

## 6. Item model

### 6.1 Item header (server-visible)

The server stores and returns this object (the "item header") in `clip` messages, history responses, and item responses:

| Field | Type | Meaning |
|---|---|---|
| `id` | string | UUIDv7 from the creating client |
| `seq` | int64 | server-assigned at commit (3.3) |
| `device_id` | string | device that created the item (from its token, never from the body) |
| `kind` | string | `text`, `image`, or `files` |
| `size` | int64 | plaintext content length in bytes (6.3), at least 1 |
| `chunk_count` | int | `0` for inline items, otherwise `ceil(size / 4194304)` |
| `created_at` | timestamp | server time at commit |
| `pinned` | bool | pin status |
| `content_hash` | string | 64 hex chars (5.3) |
| `has_thumb` | bool | a sealed thumbnail exists |
| `stored_bytes` | int64 | sum of sealed sizes: meta + payload + thumb + all chunks |
| `meta` | string | base64 sealed meta |
| `payload` | string | base64 sealed inline payload. Present only for inline items and only in `clip` messages and `GET /api/items/{id}`. Never in history responses or in create and commit responses. |

### 6.2 Encrypted meta

Meta plaintext is a compact UTF-8 JSON object, sealed with the meta AAD. Maximum sealed size 65536 bytes.

| Field | Type | Required | Meaning |
|---|---|---|---|
| `v` | int | yes | meta schema version, `1` |
| `mime` | string | yes | `text/plain; charset=utf-8` for text, `image/png` for image, `application/x-yikz-files` for files |
| `preview` | string | yes | at most 500 code points (6.4). Empty string for images |
| `sha256` | string | yes | lowercase hex SHA-256 of the full plaintext content |
| `image` | object | image only | `{"width": <px>, "height": <px>}` of the PNG |
| `files` | array | files only | `[{"name": "<name>", "size": <bytes>}, ...]` in archive order |
| `source_app` | string | no | human-readable name of the app the content was copied from, when known |

Receivers MUST ignore unknown meta fields and MUST reject meta whose `v` is not 1 (show the item as "unsupported" without failing the whole history).

### 6.3 Content per kind

- **text**: the clipboard string encoded as UTF-8, exactly as read. No Unicode normalization, no line-ending conversion, no trimming. Only plain text is synced in v1 (no RTF or HTML).
- **image**: a PNG file. Clients MUST convert other clipboard image formats (TIFF, DIB, JPEG, WebP) to PNG before sending. Receivers write the PNG to the clipboard (converting to the platform format if needed).
- **files**: a YCF1 archive (6.5) of one or more regular files.

### 6.4 Preview

`preview` is the first 500 Unicode code points of a string, with no trimming or whitespace normalization. It never splits a code point (in UTF-16 languages, never split a surrogate pair). Combining marks count as separate code points.

- text: preview of the text.
- image: `""`.
- files: preview of the file names joined with `"\n"` in archive order.

### 6.5 Files archive (YCF1)

```
magic       4 bytes   "YCF1" (59 43 46 31)
file_count  u32 big-endian
repeat file_count times:
  name_length  u32 big-endian (bytes)
  name         UTF-8, NFC
  data_length  u64 big-endian
  data         data_length bytes
```

No padding, no alignment, no trailer. The archive length is exactly `8 + sum(4 + name_length + 8 + data_length)`. Readers MUST reject trailing bytes, truncation, a `file_count` of 0 or above 1000, and any invalid name.

Name rules (senders MUST produce, receivers MUST enforce):

- a base name only, NFC normalized, 1 to 255 UTF-8 bytes,
- not `.` or `..`,
- no `/`, `\`, NUL, or any control character (U+0000 to U+001F and U+007F),
- unique within the archive (byte-wise comparison after NFC).

The archive is a flat list of regular files. Directories are not supported in v1: senders skip directories (and if nothing remains, send nothing) and resolve symbolic links to their target file. Because data lengths precede data, archives can be written and read in a streaming fashion; chunk boundaries have no relation to file boundaries. Receivers that write to case-insensitive file systems MUST resolve collisions locally (for example `name (2).ext`).

### 6.6 Thumbnails

Optional, image items only. A JPEG (quality about 80) scaled so the longest side is at most 320 px, never upscaled, sealed with the thumb AAD, at most 65536 sealed bytes (lower the quality or size until it fits). Uploaded with `PUT /api/items/{id}/thumb` before the item is created or committed.

### 6.7 Inline versus chunked

```
if size <= 262144:  inline,  chunk_count = 0, payload = seal(content)
else:               chunked, chunk_count = ceil(size / 4194304)
                    chunk i plaintext = content[i*4194304 : min((i+1)*4194304, size)]
```

Every chunk except the last holds exactly 4194304 plaintext bytes. Each chunk is sealed separately with a fresh nonce and the chunk AAD. Sealed chunk length is plaintext length + 28, so a full chunk is 4194332 bytes. See `chunking.json`.

## 7. Uploading items

The WebSocket never carries uploads. All item creation goes through HTTP.

### 7.1 Inline items: POST /api/items

For items with `size <= 262144`. Optional first step: `PUT /api/items/{id}/thumb`. Then one request:

```json
{
  "id": "<uuidv7>",
  "kind": "text",
  "size": 43,
  "chunk_count": 0,
  "content_hash": "<64 hex>",
  "meta": "<base64 sealed meta>",
  "payload": "<base64 sealed payload>"
}
```

Server validation, in order:

1. Authentication (`401`), body at most 1048576 bytes (`413 body_too_large`), valid JSON (`400 invalid_request`).
2. `id` valid (`400 invalid_id`); `kind` valid, `content_hash` 64 lowercase hex, `chunk_count` equals 0, `1 <= size <= 262144` (`400 invalid_request`).
3. Decoded `meta` is 28 to 65536 bytes (`400 invalid_request` or `413 body_too_large`); decoded `payload` length equals `size + 28` (`400 size_mismatch`).
4. Key check stored (`409 key_check_missing`).
5. If an item with this id is already committed: if `kind`, `size`, `chunk_count` and `content_hash` all match, respond `200` with the existing header (idempotent retry, nothing is broadcast); otherwise `409 id_conflict`. If chunks were uploaded for this id, `400 invalid_request`.

On success the server assigns `seq` and `created_at`, sets `has_thumb` if a thumbnail was uploaded for the id, responds `201` with the item header (without `payload`), broadcasts `clip` (with `payload`), then runs dedupe (12.3) and retention (14).

### 7.2 Chunked items

1. Optional `PUT /api/items/{id}/thumb`.
2. `PUT /api/items/{id}/chunks/{n}` for every `n` in `0 .. chunk_count-1`, in any order. Clients SHOULD upload at most 3 chunks in parallel and retry each failed chunk with backoff.
3. `POST /api/items/{id}/commit`.

**PUT /api/items/{id}/chunks/{n}**: body is the raw sealed chunk, `Content-Type: application/octet-stream`. `n` is a base-10 integer, `0 <= n < 65536`, else `400 invalid_request`. Body length must be 28 to 4194332 bytes (`400 invalid_request` below, `413 body_too_large` above; the server MUST stop reading once the limit is exceeded). Responds `204`. Uploading the same index again replaces the stored chunk (idempotent). If the id is already committed: `409 already_committed`. If the sum of pending bytes for the id would exceed the storage limit: `413 item_too_large`. Disk guard: see 7.4.

**PUT /api/items/{id}/thumb**: body is the raw sealed thumbnail, 28 to 65536 bytes. Responds `204`. Replaces a previous pending thumbnail. `409 already_committed` if the id is committed.

**POST /api/items/{id}/commit**: JSON body:

```json
{
  "kind": "files",
  "size": 8389639,
  "chunk_count": 3,
  "content_hash": "<64 hex>",
  "meta": "<base64 sealed meta>"
}
```

Validation, in order:

1. Same body, id, kind, hash and meta checks as 7.1. `size` must be greater than 262144 (`400 invalid_request`), and `chunk_count` must equal `ceil(size / 4194304)` (`400 size_mismatch`).
2. Key check stored (`409 key_check_missing`).
3. Already committed with matching `kind`, `size`, `chunk_count` and `content_hash`: `200` with the existing header. Committed with different values: `409 id_conflict`.
4. Every index `0 .. chunk_count-1` present, else `409 missing_chunks` with `details: {"missing": [indices]}` (at most 100 indices listed).
5. Every chunk has the exact expected sealed length (`4194332`, and `last_plaintext + 28` for the last), else `400 size_mismatch` with `details: {"index", "expected", "actual"}`. Chunks with index `>= chunk_count` are discarded.
6. Disk guard (7.4).
7. Total `stored_bytes` must fit in `CC_STORAGE_MAX_GB` minus the current pinned bytes, else `413 item_too_large` (the pending upload is kept until it expires or is deleted).

On success: `201` with the header (no `payload`), broadcast `clip`, run dedupe and retention.

### 7.3 Pending uploads

Chunks and thumbnails uploaded for an id that is not committed are "pending". A pending upload is deleted when no upload request for that id arrived in the last 3600 seconds, or when the client calls `DELETE /api/items/{id}` (cancel). Pending bytes are not part of `used_bytes`. Pending ids are invisible to history and `GET /api/items/{id}` (`404`).

### 7.4 Disk guard

While free disk space on the data directory's file system is below `CC_MIN_FREE_DISK_GB`, uploads larger than 1 MiB are rejected with `507 disk_low`:

- `PUT .../chunks/{n}` when `n >= 1` or the body is longer than 1048604 bytes (1 MiB + 28),
- `POST .../commit` when `size > 1048576`.

Inline creates and thumbnails are always allowed. The server re-measures free space at most every 10 s for this check. See 14.3 for the warning broadcast.

### 7.5 Body limits summary

| Request | Limit |
|---|---|
| JSON bodies | 1048576 bytes |
| Chunk body | 4194332 bytes |
| Thumbnail body | 65536 bytes |
| Sealed meta | 65536 bytes |

nginx MUST allow at least `client_max_body_size 8m`.

## 8. Downloading and managing items

All endpoints in this section are authenticated.

### 8.1 GET /api/items/{id}

`200` with the item header including `payload` for inline items. `400 invalid_id`, `404 not_found` (unknown, deleted, or pending).

### 8.2 GET /api/items/{id}/chunks/{n}

`200`, `Content-Type: application/octet-stream`, `Content-Length` set, body is the raw sealed chunk. `404 not_found` if the item or index does not exist. Range requests are not supported in v1. Clients MUST open each chunk with the chunk AAD (which includes `chunk_count` from the header), verify every chunk, and finally verify `meta.sha256` over the whole content before using it. Clients SHOULD stream chunks to a temporary file rather than hold the content in memory.

### 8.3 GET /api/items/{id}/thumb

`200` with the raw sealed thumbnail, or `404 not_found` when `has_thumb` is false.

### 8.4 GET /api/history

Query parameters: `before` or `after` (mutually exclusive, non-negative integers) and `limit` (1 to 500, default 100). Any other combination or value gives `400 invalid_request`.

- No cursor: the newest committed items, ordered by `seq` descending.
- `before=<seq>`: items with `seq < before`, `seq` descending. Used to page back through history.
- `after=<seq>`: items with `seq > after`, `seq` **ascending**. Used for catch-up.

Response `200 {"items": [<header>...], "has_more": <bool>}`. Headers never include `payload`. `has_more` is true when more items exist beyond the returned page in the same direction. The next page uses `before = last returned seq` or `after = last returned seq`.

### 8.5 GET /api/history/index

Response `200`:

```json
{"current_seq": 44, "state_rev": 17, "items": [{"id": "...", "seq": 41, "pinned": false}, ...]}
```

`items` lists every committed item, `seq` ascending. `current_seq` and `state_rev` are read in the same transaction as the list. Used for reconciliation (11.3).

### 8.6 POST /api/items/{id}/pin

Body `{"pinned": true}` or `{"pinned": false}`. Responds `200` with the updated header (no `payload`). When the value changes, the server broadcasts `clip_pinned` and increments `state_rev`. Setting the current value is a no-op (`200`, no broadcast). Pinning fails with `409 pinned_limit` when the pinned bytes plus this item's `stored_bytes` would exceed `CC_PINNED_MAX_GB`. `404 not_found` for unknown ids.

### 8.7 DELETE /api/items/{id}

Deletes a committed item (`204`, broadcast `clip_deleted` with reason `user`) or cancels a pending upload (`204`, no broadcast). `404 not_found` if neither exists. Clients MUST treat `404` as success when deleting.

### 8.8 GET /api/storage

```json
{
  "used_bytes": 8391704, "limit_bytes": 5368709120,
  "pinned_bytes": 456, "pinned_limit_bytes": 1073741824,
  "item_count": 4,
  "free_disk_bytes": 11811160064, "min_free_disk_bytes": 2147483648,
  "retention_days": 7, "disk_low": false
}
```

`used_bytes` is the sum of `stored_bytes` of all committed items. `pinned_bytes` is the same sum over pinned items. Values in this example come from vector `storage`.

### 8.9 GET /healthz

No authentication. `200 {"status": "ok", "server_version": "1.0.0", "protocol_version": 1}`.

### 8.10 Other

Unknown routes give `404 not_found`. A known route with the wrong method gives `405 method_not_allowed`. The web UI is served from the same origin, so no CORS headers are sent.

## 9. Errors

### 9.1 Shape

Every non-2xx HTTP response has `Content-Type: application/json; charset=utf-8` and this body:

```json
{"code": "not_found", "message": "item not found", "details": {}}
```

`code` is machine-readable and stable. `message` is human-readable English and may change. `details` is optional and code-specific. Clients MUST branch on `code` and HTTP status only. Successful JSON responses also use `application/json; charset=utf-8`. `204` responses have no body.

### 9.2 HTTP error codes

| Code | Status | Where | Client action |
|---|---|---|---|
| `invalid_request` | 400 | any | bug, do not retry |
| `invalid_id` | 400 | any path or body with an item id | bug, do not retry |
| `size_mismatch` | 400 | create, commit | bug, do not retry; `details` on commit |
| `invalid_credentials` | 401 | login | ask for credentials again |
| `unauthorized` | 401 | every authenticated endpoint, `/ws` upgrade | drop token, require login |
| `not_found` | 404 | items, chunks, thumb, devices, unknown routes | treat as gone |
| `method_not_allowed` | 405 | any | bug |
| `id_conflict` | 409 | create, commit | generate a new id and re-encrypt |
| `already_committed` | 409 | chunk and thumb upload | stop uploading, fetch the item |
| `missing_chunks` | 409 | commit | upload `details.missing`, then commit again |
| `key_check_missing` | 409 | create, commit, chunk, thumb | run the key check flow (5.4) |
| `key_check_exists` | 409 | PUT key-check | compare with `/api/me` value |
| `items_exist` | 409 | DELETE key-check | delete items first |
| `pinned_limit` | 409 | pin | tell the user |
| `body_too_large` | 413 | any upload | bug, do not retry |
| `item_too_large` | 413 | chunk upload, commit | tell the user, delete the pending upload |
| `rate_limited` | 429 | login | wait `Retry-After` seconds |
| `internal` | 500 | any | retry with backoff |
| `disk_low` | 507 | chunk upload, commit | tell the user, retry later |

Network errors, `500`, `502`, `503` and `504` are retried with exponential backoff (1 s doubling to 60 s, full jitter). Other `4xx` are not retried automatically.

### 9.3 WebSocket error codes

Sent as `{"type":"error","code":...,"message":...,"details"?}`.

| Code | Followed by | Meaning |
|---|---|---|
| `protocol_version_unsupported` | close 4003 | `hello.protocol_version` not supported; `details.supported` lists supported versions |
| `device_mismatch` | close 4001 | `hello.device_id` differs from the token's device |
| `hello_required` | close 4004 | first message was not `hello` |
| `invalid_message` | nothing | frame is not a JSON object with a string `type`; connection stays open |
| `unknown_type` | nothing | unknown `type`; connection stays open |

## 10. WebSocket

### 10.1 Connecting

`GET /ws` upgraded to WebSocket, authenticated by `Authorization: Bearer` or `?token=` (4.2). A bad token fails the upgrade with `401 unauthorized` (vector `ws_upgrade_unauthorized`). Only text frames carrying one JSON object each are used. Clients MUST accept server messages up to 1048576 bytes (an inline `clip` can be about 450 KB). The server rejects client messages larger than 65536 bytes by closing with 1009.

A device may hold up to 8 concurrent connections (for example several browser tabs). When a 9th completes its handshake, the server closes the oldest connection of that device with 4002.

### 10.2 Handshake

1. The client sends `hello` immediately after the socket opens. Before `welcome` it may send only `hello`, `ping` and `pong`.
2. The server validates it. Unsupported version: `error protocol_version_unsupported`, close 4003. Device id differs from the token's device: `error device_mismatch`, close 4001. First message not `hello`: `error hello_required`, close 4004. No `hello` within 10 s: close 4004.
3. The server sends `welcome`, then `storage_warning` with `active: true` if the disk is currently low, then live events. The server registers the connection for broadcasts **before** reading `current_seq` for `welcome`, so no item committed after `current_seq` can be missed.
4. If this is the device's first live connection, the server broadcasts `presence` with `online: true` to all other connections.

### 10.3 Messages

Every message has a string `type`. Examples for each are in `ws.json`.

**hello** (client to server)

| Field | Type | Meaning |
|---|---|---|
| `protocol_version` | int | `1` |
| `device_id` | string | this device's id |
| `last_seq` | int64 | the client's persisted `last_seq` (11.1), 0 if none. Informational: the server MAY log it and MUST NOT replay items over the WebSocket |
| `app_version` | string | client build version |
| `platform` | string | `macos`, `android`, `windows`, `web` |

**welcome** (server to client)

| Field | Type | Meaning |
|---|---|---|
| `protocol_version` | int | `1` |
| `server_version` | string | informational |
| `server_id` | string | 3.2 |
| `server_time` | timestamp | server clock at send time |
| `device_id` | string | the caller's device id |
| `current_seq` | int64 | highest seq assigned |
| `state_rev` | int64 | current state revision |
| `online_devices` | array | `[{"device_id","name","platform"}]` for every online device, including the caller |

**presence** (server to client): `device_id`, `name`, `platform`, `online` (bool). Sent when a device gets its first live connection or loses its last one. Not sent to the connections of the device itself.

**devices_changed** (server to client): no fields. The device list changed (login, rename, revoke, removal). Clients showing devices re-fetch `GET /api/devices`.

**clip** (server to client): `item`, the full item header including `payload` for inline items. Sent to every live connection, including the connections of the device that created the item, in `seq` order.

**clip_deleted** (server to client): `ids` (array of 1 to 500 item ids), `reason` (`user`, `retention`, or `dedupe`), `state_rev` (the new value). Larger deletions are split into several messages.

**clip_pinned** (server to client): `id`, `pinned` (bool), `state_rev` (the new value).

**storage_warning** (server to client): `active` (bool), `reason` (`disk_low`), `free_disk_bytes`, `min_free_disk_bytes`. Clients show a persistent warning while the last received message has `active: true`.

**ping** (both directions): `ts`, the sender's clock in Unix milliseconds.

**pong** (both directions): `ts`, copied from the `ping` it answers. The receiver of a `ping` MUST answer with `pong` promptly.

**error** (server to client): `code`, `message`, optional `details` (9.3).

Receivers MUST ignore unknown fields. Clients MUST silently ignore unknown message types. The server answers unknown types with `error unknown_type`. Clients never send `clip`, `clip_deleted` or `clip_pinned`.

### 10.4 Heartbeat

- Both sides send an application `ping` message every 20 s while connected.
- Each side tracks the time since it last received any message (any type, including `pong`). If it reaches 45 s, the connection is dead: the server closes with 4005; the client closes (4005 or simply aborts) and reconnects with backoff.
- WebSocket protocol-level ping and pong frames MAY also be used (for example OkHttp `pingInterval`) but do not replace the JSON `ping`, and the server does not count them as traffic.
- nginx MUST use `proxy_read_timeout 3600s; proxy_send_timeout 3600s; proxy_buffering off;`.

### 10.5 Close codes

| Code | Meaning | Client action |
|---|---|---|
| 1000 | normal close | reconnect with backoff unless quitting or logging out |
| 1001 | server shutting down | reconnect with backoff |
| 1009 | client message too large | bug; reconnect with backoff |
| 4001 | unauthorized (token revoked) or device_mismatch | do not reconnect; require login |
| 4002 | closed because the device exceeded 8 connections | do not reconnect automatically; reconnect on user action or when returning to foreground |
| 4003 | protocol_version_unsupported | do not reconnect; tell the user to update |
| 4004 | no or invalid `hello` | reconnect with backoff |
| 4005 | heartbeat timeout | reconnect with backoff |

Any other close or network error: reconnect with backoff.

### 10.6 Reconnect

```
attempt  = 0 after every received welcome
delay(n) = uniform_random(0, min(30, 0.5 * 2^n)) seconds     (full jitter)
```

After each failed or closed connection the client waits `delay(attempt)` and then increments `attempt`.

Immediate reconnect (set `attempt = 0`, cancel any pending timer, connect now):

- **Wake from sleep** (macOS `NSWorkspace.didWakeNotification`, Windows `SystemEvents.PowerModeChanged` Resume) and **network change or network available** (`NWPathMonitor`, `ConnectivityManager.NetworkCallback`, `NetworkChange.NetworkAvailabilityChanged`, browser `online` event): always close the current socket, even if it looks open, and reconnect.
- **App to foreground** (Android lifecycle, browser `visibilitychange` to visible): if disconnected, reconnect now. If connected, send a `ping` and reconnect if no message arrives within 5 s.

## 11. Client sync algorithm

### 11.1 Persisted client state

| Name | Meaning |
|---|---|
| `server_id` | from the last welcome |
| `last_seq` | highest seq fully caught up to |
| `state_rev` | last reconciled state_rev, or none |
| `applied_seq` | highest seq considered for auto-apply |
| local cache | decrypted item headers and meta, keyed by id |

### 11.2 On welcome

1. **Server change**: if `welcome.server_id` differs from the stored `server_id` (and one is stored), clear the local cache and set `last_seq = 0`, `state_rev = none`, `applied_seq = 0`. Re-fetch `/api/me`; if `salt` changed or the key check fails, discard `K` and ask for the encryption password again. Store the new `server_id`.
2. **Clock offset**: `offset = welcome.server_time - local_now_at_receipt`. Server time is estimated as `local_now + offset`.
3. **Initial sync** (`last_seq == 0`): page backwards with `GET /api/history?before=<welcome.current_seq + 1>` (then `before = smallest seq returned`) until `has_more` is false or the client has enough history. Set `last_seq = welcome.current_seq` and `applied_seq = welcome.current_seq`. Nothing is auto-applied on initial sync.
4. **Catch-up** (`last_seq > 0` and `welcome.current_seq > last_seq`): request `GET /api/history?after=<cursor>&limit=500` starting with `cursor = last_seq`, insert every returned item, set `cursor` to the last returned seq, and repeat while `has_more`. When finished, set `last_seq = max(cursor, highest seq received live meanwhile)`. Only this step advances the persisted `last_seq` until it completes, so an interrupted catch-up never skips items.
5. **Reconcile** when `welcome.state_rev != state_rev` (or `state_rev` is none): see 11.3.
6. Run auto-apply over the items inserted in step 4 (11.5).

Live `clip` events that arrive during steps 3 to 5 are inserted into the cache immediately (insertion by id is idempotent). After catch-up completes, every live `clip` sets `last_seq = max(last_seq, seq)`.

This is the only catch-up mechanism: the WebSocket never replays missed items.

### 11.3 Reconciliation

Call `GET /api/history/index`. Delete every cached item whose id is not in `items`. Set `pinned` from the index for every cached item. Items in the index that are missing from the cache MAY be fetched lazily with `GET /api/items/{id}` or `GET /api/history?before=`. Store `state_rev` from the index response.

On a live `clip_deleted` or `clip_pinned`: apply it to the cache. If `event.state_rev == state_rev + 1`, store it. If it is greater, events were missed: store nothing and run reconciliation. If it is less or equal, ignore the counter (the change is still applied idempotently).

### 11.4 Decryption

For every header: decrypt `meta` with the meta AAD and cache the parsed meta. For inline items, the `payload` (from `clip` or `GET /api/items/{id}`) decrypts with the payload AAD. Before writing content to the clipboard or to disk as a finished file, the client MUST check that SHA-256 of the full content equals `meta.sha256` and that `content_hash` recomputed with its own key equals the header value. On any mismatch or AEAD failure, discard the content and log an error.

### 11.5 Auto-apply to the system clipboard

Only one item per burst is written to the system clipboard: the newest item not from this device, created within the last 5 minutes. Everything else only appears in history.

```
age(item)     = (local_now + offset) - item.created_at
eligible(item) = item.device_id != own device_id
                 and item.seq > applied_seq
                 and age(item) <= 300 s
```

- After catch-up (11.2 step 4): among the items inserted by catch-up and the live items received during it, take the eligible item with the highest seq and apply it. Then set `applied_seq` to the highest seq among all of them, whether applied or not.
- Live, after catch-up: for each `clip`, if eligible, apply it. Always set `applied_seq = max(applied_seq, seq)`.
- Items from this device are never auto-applied (the local clipboard already holds them).

Applying an item:

- Inline: decode the payload and write.
- Chunked with `size <=` the device's auto-download limit (default 52428800, user configurable per device): download all chunks, verify, then write.
- Chunked above the limit: show a notification such as "File X (200 MB) from Pixel 9, download?". The item stays downloadable from history until it expires.
- Before writing a downloaded item, check that no item with a higher seq was applied in the meantime; if one was, do not write.
- The web client writes only while the page is visible and the Clipboard API allows it; otherwise it only shows the item in history.

## 12. Echo-loop prevention and dedupe

### 12.1 Suppressing own writes

When a client writes a received item to the clipboard it MUST:

1. Record the platform's clipboard change marker right after writing (macOS `NSPasteboard.changeCount`, Windows `GetClipboardSequenceNumber`) and ignore the clipboard change that carries that marker. Android ignores the next `OnPrimaryClipChangedListener` callback that follows its own `setPrimaryClip`.
2. Add the item's `content_hash` to a recent-hash set (the last 32 hashes of items applied, sent, or received).
3. SHOULD add a private marker so its own watcher can recognize the content: pasteboard type `dev.yikz.clipboard.origin` (macOS), registered clipboard format `YikzClipboardOrigin` (Windows), or `ClipDescription` extras key `dev.yikz.clipboard.origin` (Android), each carrying the item id. Content carrying the marker is never uploaded.

### 12.2 Before uploading a local change

1. Skip sensitive content (13.2).
2. Build the content (6.3) and compute `content_hash`.
3. Skip if `content_hash` is in the recent-hash set. For text, also compute the hash of the text with every `\r\n` replaced by `\n` and skip if that matches.
4. Skip if `content_hash` equals the `content_hash` of the newest item in the local cache (the item is already current everywhere).
5. Otherwise upload with a new id and add the hash to the set.

### 12.3 Server-side dedupe

After an item is committed (7.1 or 7.2), the server deletes every other **non-pinned** committed item with the same `content_hash`, and broadcasts one `clip_deleted` with reason `dedupe`. The effect is that copying an older item again moves it to the top instead of creating a duplicate. Pinned duplicates are kept.

## 13. Capturing and writing the clipboard

### 13.1 Choosing the representation

When the clipboard holds several representations, clients SHOULD pick in this order: file URLs (kind `files`), then an image (kind `image`), then plain text (kind `text`). Exception: when the clipboard also holds rich text (macOS `public.rtf`, Windows `Rich Text Format`), text wins over an image (office apps put a rendered image next to the text). Empty text is never sent.

Detection: macOS polls `NSPasteboard.changeCount` every 300 ms. Windows uses `AddClipboardFormatListener`. Android cannot read in the background; sending is user-triggered (Quick Settings tile, notification action, share target) or uses the optional `READ_LOGS` mode. The web client sends on explicit paste or drop.

Receiving files: write them into a per-item folder in the app's cache directory (cleaned automatically), then place file URLs on the clipboard (macOS `NSURL` objects, Windows `CF_HDROP` or storage items, Android `content://` URIs from a `FileProvider` with `ClipData.newUri`, web offers downloads).

### 13.2 Sensitive content

Content matching any rule below MUST NOT be uploaded and MUST NOT be added to local history:

| Platform | Rule |
|---|---|
| macOS | the pasteboard contains type `org.nspasteboard.ConcealedType` or `org.nspasteboard.TransientType` (clients SHOULD also skip `org.nspasteboard.AutoGeneratedType`) |
| Windows | the clipboard contains the registered format `ExcludeClipboardContentFromMonitorProcessing`, or the format `CanIncludeInClipboardHistory` with DWORD value 0 (clients SHOULD also skip `CanUploadToCloudClipboard` with DWORD 0) |
| Android | `ClipDescription.getExtras()` has `ClipDescription.EXTRA_IS_SENSITIVE` (`android.content.extra.IS_SENSITIVE`) set to true |
| Web | not applicable (only explicit user actions) |

## 14. Server retention and storage

### 14.1 Configuration

| Env var | Default | Unit |
|---|---|---|
| `CC_RETENTION_DAYS` | 7 | days |
| `CC_STORAGE_MAX_GB` | 5 | GiB |
| `CC_PINNED_MAX_GB` | 1 | GiB |
| `CC_MIN_FREE_DISK_GB` | 2 | GiB |

Plus `CC_USERNAME`, `CC_PASSWORD`, `CC_LISTEN`, `CC_DATA_DIR`. Stored bytes always mean ciphertext sizes: the `stored_bytes` of an item is the sum of its sealed meta, payload, thumbnail and chunk lengths.

### 14.2 Retention run

Runs every 15 minutes and after every successful create or commit (after dedupe):

1. Delete pending uploads idle for more than 3600 s (no broadcast).
2. Delete every non-pinned item with `created_at` older than `now - CC_RETENTION_DAYS`.
3. While `used_bytes > CC_STORAGE_MAX_GB`, delete the non-pinned item with the lowest `seq`, never the item that was just committed.
4. If anything was deleted in steps 2 and 3, broadcast `clip_deleted` with reason `retention` (split at 500 ids per message, one `state_rev` increment per message).

Pinned items are exempt from steps 2 and 3 but count toward `used_bytes`. Total pinned `stored_bytes` may not exceed `CC_PINNED_MAX_GB`; this is enforced when pinning (`409 pinned_limit`).

### 14.3 Disk guard warning

The server checks free disk space every 60 s. When it drops below `CC_MIN_FREE_DISK_GB`, it broadcasts `storage_warning` with `active: true`; when it rises back to at least that value, it broadcasts `active: false`. Connections that complete a handshake while the disk is low receive `active: true` right after `welcome`. While low, uploads follow 7.4.

## 15. Versioning

- `protocol_version` is `1`. It appears in login, `/api/me`, `/healthz`, `hello` and `welcome`.
- A server supports a list of versions (currently `[1]`). A `hello` with an unsupported version gets `error protocol_version_unsupported` with `details.supported`, then close 4003.
- A client that sees a `protocol_version` it does not support in login, `/api/me` or `/healthz` MUST stop syncing and tell the user to update the app.
- Adding optional fields, message types or error codes does not change the version. Clients MUST tolerate them (ignore unknown fields and types, treat unknown error codes by HTTP status).
- Meta has its own `v` (6.2); the YCF1 magic versions the archive format.

## 16. Test vectors

All files live in `protocol/vectors/`. They are produced by running `protocol/tools/genvectors` (Go) and checked by the independent Python verifier `protocol/tools/verify/verify_vectors.py`. Every platform MUST load these files in its unit tests. Nonces in vectors are fixed (derived from labels) only to make the output deterministic; real code MUST use random nonces, so tests compare by calling a seal function that accepts an explicit nonce, and compare decryption output for everything else.

Common fixture: encryption password `correct horse battery staple`, salt hex `5c1e8f2a9b3d47e6a0c4f81d2e6b9a73`, primary key `445b4a046c63fd1e1aa196088b1b75665ecba3d831addb5bf5a9908236767294`, username `thoriq`, login password `login-password-example`.

Each file is a JSON object with a `description` string plus the fields below.

### kdf.json

- `algorithm` (`pbkdf2-sha256`), `key_length` (32).
- `cases[]`: `name`, `password_input` (as typed), `password_normalized` (NFC), `password_utf8_hex` (bytes fed to PBKDF2), `salt_b64`, `salt_hex`, `iterations`, `key_hex`.
- Cases: `primary` (600000 iterations), `fast` (1000 iterations, for fast unit tests only), `unicode_nfd_input` (NFD input that must be normalized to NFC).

### keys.json

- `content_hash_label_utf8`, `key_check_label_utf8`: the HMAC labels.
- `keys[]`: `name` (`primary`, `fast`, matching kdf.json), `key_hex`, `content_hash_key_hex`, `key_check`, `content_hash_samples[]` with `content_utf8`, `content_hex`, `content_hash`, `sha256`.

### aead.json

- `aad_formats`: object mapping `meta`, `payload`, `thumb`, `chunk` to their AAD templates.
- `positive[]`: `name`, `purpose`, `key_hex`, `nonce_hex`, `aad_utf8`, `aad_hex`, `plaintext_hex`, optional `plaintext_utf8`, `sealed_hex`, `sealed_b64`, `sealed_length`. Test: seal(key, nonce, aad, plaintext) equals `sealed_hex`, and open gives the plaintext.
- `negative[]`: `name`, `reason`, `key_hex`, `aad_utf8`, `aad_hex`, `sealed_hex`, `sealed_b64`, `expect` (`decrypt_error`). Opening MUST fail (tampering, swapped chunk index, changed chunk count, moved meta, purpose confusion, wrong key, too short).

### uuidv7.json

- `regex`: the id pattern (3.1).
- `generate[]`: `unix_ms`, `random_hex` (10 bytes before the version and variant bits are applied), `expected`.
- `valid[]`: strings that MUST be accepted.
- `invalid[]`: `value`, `reason`; MUST be rejected.

### files_archive.json

- `cases[0]` (`three_files`): `files[]` with `name`, `name_utf8_hex`, `size`, `data_hex`; `archive_hex`, `archive_size`, `archive_sha256`. Test pack and unpack.
- `cases[1]` (`single_large_file_header`): `files[0]` with `name`, `size`, `data_rule` (byte i = i mod 251); `archive_prefix_hex` (magic, count, name length, name, data length), `archive_size`, `archive_sha256`.
- `invalid_names[]`: `name`, `reason`; each MUST be rejected by the name rules.

### chunking.json

- `inline_max_bytes`, `chunk_size_bytes`, `seal_overhead_bytes`.
- `cases[]`: `size`, `inline`, `chunk_count`; inline cases add `payload_sealed_length`; chunked cases add `full_chunk_plaintext_size`, `full_chunk_sealed_length`, `last_chunk_index`, `last_chunk_plaintext_size`, `last_chunk_sealed_length`, `total_chunk_sealed_bytes`.

### preview.json

- `max_code_points` (500).
- `cases[]`: `name`, `input`, `input_code_points`, `input_utf16_units`, `expected`, `expected_code_points`. Covers emoji at the boundary and combining marks.

### token.json

- `regex`: token pattern.
- `cases[]`: `random_hex` (32 bytes), `token`, `token_hash`.

### items.json

`items[]`, one per fixture item (`text` inline, `image` inline PNG with JPEG thumbnail, `files` inline pinned YCF1 archive of three files, `large` chunked files item of 3 chunks):

- `name`, `description`, `key_hex`, `id`, `kind`, `size`, `chunk_count`.
- Content: inline items have `content_hex` (and `content_utf8` for text); the chunked item has `content_rule` instead (rebuild it from files_archive.json `single_large_file_header`).
- `content_sha256`, `content_hash`.
- Meta: `meta_plaintext_utf8` (exact bytes that were sealed), `meta` (parsed), `meta_aad_utf8`, `meta_nonce_hex`, `meta_sealed_b64`.
- Inline: `payload_aad_utf8`, `payload_nonce_hex`, `payload_sealed_b64`.
- Thumbnail (image): `thumb_plaintext_hex`, `thumb_aad_utf8`, `thumb_nonce_hex`, `thumb_sealed_b64`.
- Chunked: `chunks[]` with `index`, `aad_utf8`, `nonce_hex`, `plaintext_size`, `plaintext_sha256`, `sealed_size`, `sealed_sha256`, `sealed_prefix_hex` (first 44 bytes), `sealed_suffix_hex` (last 32 bytes).
- `stored_bytes`, `header` (the item header as the server returns it in `clip`, including `payload` for inline items).

### http.json

`examples[]`: `name`, `method`, `path` (including query), optional `request_headers`, optional `request_body` (JSON, or a base64 string for binary bodies), optional `request_body_note`, `status`, optional `response_headers`, optional `response_body`, optional `response_body_note`. When a note says a body is raw bytes, the base64 string in the vector is only a readable rendering; on the wire the body is binary. Examples are independent snapshots (for example `item_delete` and `unpin` each start from the fixture state), and all item fields decrypt with the primary key. Server tests SHOULD replay them; client tests SHOULD parse every response body.

### ws.json

- `close_codes[]`: `code`, `meaning`, `client_action` (10.5).
- `messages[]`: `name`, `direction` (`client_to_server` or `server_to_client`), `message` (the exact JSON object of one text frame).
